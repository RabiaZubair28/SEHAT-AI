# Health Advisor AI integration

The current Advisor screen flow now uses a single LLM response for findings, recommendations, meals and handout content, with no rule-based generation fallback. See [SETUP.md](SETUP.md) for the current configuration. The sections below describe the earlier food-only drafting path, which remains in source for compatibility and tests but is not used by the screen's generation endpoint.

The latest user request adds LLM drafting to the existing rules-based advisor. The Health Advisor PDF instead specifies a non-LLM MILP solver; the overall proposal permits AI assistance. This implementation follows the latest request and does not implement MILP or claim clinical validation.

## How factors affect the result

Factors should not receive equal weights. First determine eligibility, then calculate targets, then enforce food restrictions. Optimize preferences only within that feasible space.

| Factor group | Current handling |
| --- | --- |
| Age and sex | Existing eligibility checks and energy equations; included in model context |
| Weight, height, BMI | Existing validation and target calculation; effective corrected measurements included |
| Activity | Existing target multiplier; activity level included in context |
| Recorded conditions and patient-reported conditions | Existing derived restrictions and referral gates; finding kinds retained |
| Labs and vitals | Existing evidence-based findings; model receives finding status, including missing/outdated |
| Pregnancy, lactation, complications, unsupported populations | Existing eligibility gate runs before the model call |
| Allergies | Existing catalog exclusion; disallowed identifiers rejected before repair |
| Diet type and medical restrictions | Existing catalog exclusions and final validation |
| Dislikes and availability | Explicitly excluded catalog IDs are prohibited |
| Budget | Model receives budget and each food's cost tier; soft preference, not a verified rupee limit |
| Preferred foods | Model preference within the eligible catalog |
| Variety | Model instruction plus existing deterministic repair |

The model receives all calculated nutrient targets and per-serving catalog nutrients. Its priority order is nutrient fit, affordability, preference, then variety. This is an explicit prompt policy, not a mathematically guaranteed optimizer or a clinically established weighting scheme. Calories and several other nutrient deviations remain warnings under the existing validator; a successful AI response does not establish nutritional adequacy.

## Request and validation pipeline

1. EMR authenticates the user and loads the authorized encounter.
2. Existing assessment validates inputs, determines eligibility, and calculates targets/findings/recommendations.
3. `buildPlanContext` constructs a versioned whitelist of model inputs. Names, record IDs, contact details and the full chart are omitted. Free-text notes remain untrusted and may contain personal information entered by staff.
4. The backend calls Gemini `generateContent` with system instructions and structured JSON output.
5. Local validation requires exactly seven days, exactly five slots per day, permitted slot-specific food IDs, practical array sizes, no duplicates and no extra output fields.
6. Existing deterministic repair adds structure/variety and adjusts portions. Nutrition totals are calculated locally.
7. Final restriction checks reject unsafe output. Provider errors, invalid output or missing credentials use the rule-based fallback. Fallback plans also pass error checks and must have food in every meal; otherwise the API returns HTTP 422 for manual assessment.
8. Existing versioning, clinician review and approved delivery workflows apply.

Findings, clinical recommendations and activity advice remain generated by existing clinical rules. The LLM currently drafts food selections only. This avoids making generated claims the authority for diagnoses or targets.

## Run locally

Set these variables in `emr-backend/.env`, then restart the EMR backend:

```dotenv
NUTRITION_ADVISOR_AI_ENABLED=true
GEMINI_API_KEY=your_server_side_key
NUTRITION_ADVISOR_MODEL=gemini-2.5-flash-lite
NUTRITION_ADVISOR_AI_TIMEOUT_MS=60000
```

The model is configurable; the default preserves the existing provider choice. Check model availability for your account. Never place the key in frontend configuration. Generate a plan from the existing Advisor UI; `generatedBy` distinguishes `ai:<model>` from `rules`, and fallback responses include `generationNote`.

From the workspace root:

```sh
npm test --prefix sehat-ai/apps/health-advisor/backend
npm run build --prefix sehat-ai/apps/health-advisor/backend
npm run build --prefix emr-backend
```

Tests use synthetic data and mocked provider calls. Dependencies for Jest are supplied by the host EMR backend. A live provider run is a separate integration check and incurs provider usage.

## Free prototype approach and EMR boundary

Decision recorded November 11, 2026: retain the LLM-drafting architecture and evaluate free model options before changing the runtime default. Keep model clients, prompts, validation, planning, evaluation and feature UI in `sehat-ai/`. EMR supplies authentication, authorized context, persistence and feature mounting through minimal adapters. No additional EMR edits are needed to compare model candidates using `NUTRITION_ADVISOR_MODEL`.

The recommended experiment is the existing Gemini model versus `gemini-3.5-flash-lite` and `gemini-3.8-flash`, where available to the project on the unpaid tier. Google's current pricing lists free standard input/output for the latter two. Its deprecation page says stable `gemini-2.5-flash-lite` remains available, with 2.5 access restricted to existing active users; `gemini-2.5-flash` has a different lifecycle. Do not confuse stable and preview identifiers. Pricing and account access do not prove which model is best for meal planning.

Alternatives explored:

| Approach | Fit at this stage |
| --- | --- |
| Gemini free-tier structured drafting | Recommended first experiment; reuses the implemented client and validation |
| Groq-hosted models | Possible independent benchmark; requires a separate adapter and model-specific structured-output checks; no demonstrated advantage for this app yet |
| Local Qwen3 through Ollama | No hosted per-request API fee and can keep inference local; practical speed and model size depend on available hardware; existing Ollama client is not wired into the active service |
| MILP/constrained optimizer | Useful later for verifiable cost/nutrient tradeoffs; complements the requested LLM approach, but is not implemented here |

Google's unpaid-service terms explicitly say not to submit sensitive, confidential or personal information. Use synthetic patient cases for the free hosted prototype. Omitting names alone does not establish that clinical context is anonymous. Actual patient use requires a separately suitable deployment/data-processing arrangement. Local inference avoids sending inference inputs to a hosted provider, but does not itself establish clinical suitability.

Free quotas are project/account dependent. Keep billing disabled for a strict zero-provider-spend experiment, use one bounded call per generation, and fall back locally when the quota is exhausted. Do not add paid fallback, live web search, a vector database, fine-tuning or autonomous tool access without a measured need. Confirm API/schema compatibility and run the same cases before adopting a newer model; no newer-model live call has been verified here.

Use 20–30 synthetic cases for the first comparison, including conflicting preferences, common condition combinations and deliberately unsafe/unsupported inputs. Record raw proposal validity, post-repair constraint violations, nutrient deviation, preference/cost-tier fit, variety, fallback rate, latency and actual token usage. Report raw and repaired results separately so repair does not hide weak model output. Select the model only after reviewing results. New tests alone cannot establish clinical correctness.

## Next evaluation phase

Create a clinician-reviewed synthetic case set covering common combinations and conflicting preferences. Measure acceptance rate, fallback rate, allergen/restriction violations, nutrient deviations by day, cost-tier fit, preference coverage, variety and latency. Compare the same cases against the deterministic baseline. Use those results to decide whether to add a bounded repair retry or a constrained optimizer. Do not select numerical weights without documenting their units, normalization and evaluation results.

The proposal also mentions admission reason, supplements, additional lab panels, meal schedules and hydration habits. These are not newly implemented input fields here. The food catalog and clinical thresholds still require the review described in the proposal. Prompt injection resistance uses separation of instructions/data plus deterministic output validation; prompt wording alone is not a security guarantee.
